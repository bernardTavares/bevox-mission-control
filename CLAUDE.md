## Codebase Knowledge Graph

This repository has **two complementary knowledge graphs** installed
locally. Both run entirely on Bernard's machine, no data leaves the host.

| Tool | Index | Purpose | MCP name |
|---|---|---|---|
| `codegraph` (colbymchenry, MIT) | `.codegraph/codegraph.db` | Full symbol graph — functions, classes, imports, call chains. 1.3k nodes / 1.9k edges. Served globally via `~/.claude.json` → `codegraph serve --mcp`. | `codegraph` |
| `code-review-graph` (tirth8205, MIT) | `.code-review-graph/graph.db` | Structural/review-oriented graph — blast radius, affected flows, test coverage, community clusters. 671 nodes / 5625 edges. Served per-project via `.mcp.json` → `uvx code-review-graph serve`. | `code-review-graph` |

Both are auto-updated: `code-review-graph` via Claude Code hooks in
`.claude/settings.json` (PostToolUse after Edit/Write/Bash), and
`codegraph` via `codegraph sync` (manually or cron).

### Rules — consult the graph BEFORE exploring files

- **Before any change to existing code:** check blast radius via the
  graph (`get_impact_radius` / `codegraph_explore`). Never modify a
  function without knowing who depends on it.
- **Before grep/glob/Read on the codebase:** query the graph first. If
  the graph doesn't have what you need, fall back to file tools.
- **If a dependency chain is 3+ levels deep:** use plan mode before
  editing.
- **Before committing:** run `code-review-graph detect-changes` on
  the staged files if you want risk-scored review context (the
  `PreCommit` hook does this automatically).

### Which tool for what

| Task | Tool | Primary MCP call |
|---|---|---|
| "Who calls this function?" | either | `query_graph callers_of=...` or `codegraph_query` |
| "What breaks if I change X?" | `code-review-graph` | `get_impact_radius` |
| "Find a symbol by name" | `codegraph` | `codegraph_query` |
| "Risk-scored diff review" | `code-review-graph` | `detect_changes` + `get_review_context` |
| "High-level architecture map" | `code-review-graph` | `get_architecture_overview` + `list_communities` |
| "Test coverage for a symbol" | `code-review-graph` | `query_graph tests_for=...` |

### Fallback to file tools

Grep / Glob / Read are still available. Use them when:
- The graph is stale (check `code-review-graph status` or `codegraph status`).
- You need the raw file contents (graph gives you metadata, not source).
- You're working on a file the graph doesn't cover (e.g. `.md`, `.yml`,
  `.sh`) — Tree-sitter only parses the 19 code languages in
  `codegraph`'s supported list.

### Governance notes (tied to `~/.openclaw/CLAUDE.md`)

- **Read-only approvals**: this project has `(dashboard)/approvals/`
  which is UI-side read-only. The decision surface is Telegram /
  knowledge-sync CLI, not this UI. Never add approve/reject buttons here.
- **No hidden mutations**: if you ever add a mutation path in this repo
  (POST / DELETE on the app's own API), document it explicitly in the
  PR and make sure it goes through `.openclaw/CLAUDE.md`'s approval
  policy.
- **Graph DB is cache, not source of truth**: both databases can be
  deleted at any moment and rebuilt from `codegraph index` or
  `code-review-graph build`. Never check in binary DB files — they are
  gitignored.

## Canonical Roadmap Discipline

`~/bevox-knowledge/40_roadmap/company-os/2026-04-09-openclaw-company-os-roadmap.md`
is the canonical high-level roadmap for OpenClaw Company OS.

### Mandatory roadmap sync rule

Whenever a change materially affects roadmap status, you must update the
canonical roadmap in the same workstream before considering the task complete.

Materially affects roadmap status includes:
- a wave delivered
- a feature newly delivered
- a status change (`pending` -> `partial`, `partial` -> `wave 1 delivered`, etc.)
- a new follow-up explicitly accepted into scope
- a previously accepted gap now closed
- a roadmap interpretation changed by approved spec

If you create or implement a new spec that changes epic/wave reality, you must
also update:
- the epic `Status:` line in the roadmap
- the relevant feature coverage notes for that epic
- the recommended execution order / phase notes if they changed
- the "Ultima sync com estado real" date near the top of the roadmap

### Source-of-truth precedence

When there is conflict:
1. accepted ADRs define architectural decisions
2. accepted specs define implementation reality for an epic/wave
3. the roadmap must be updated to reflect that reality
4. operational runtime files are never the canonical source for roadmap status

Do not infer roadmap completion from local runtime state alone.

### Classification vocabulary

Always use one of these exact categories when updating roadmap status:
- `entregue`
- `foundation entregue`
- `wave 1 entregue`
- `parcial`
- `pendente`
- `follow-up`
- `gap aceito`
- `fora de escopo`

Do not invent ad hoc status labels in the roadmap.

### End-of-task checklist for roadmap-affecting work

Before closing any roadmap-affecting task, verify whether these files need updates:
- `~/bevox-knowledge/40_roadmap/company-os/2026-04-09-openclaw-company-os-roadmap.md`
- relevant file(s) in `~/bevox-knowledge/35_specs/`
- relevant ADR or architecture doc if the boundary/governance changed
- release notes if the wave was meaningfully closed

If roadmap sync is still pending, explicitly say so in the final response.
Do not silently leave the roadmap stale.

### Anti-drift guardrails

- Do not add a new spec without checking whether roadmap status must change.
- Do not mark an epic fully delivered if only one wave was delivered.
- Do not treat follow-up as blocker unless the roadmap/spec says so.
- Do not create parallel trackers that replace the roadmap as strategic source of truth.
- Mission Control and runtime state are projections, not roadmap truth.

### If unsure

If it is unclear whether a change is roadmap-affecting, default to:
- checking the roadmap
- checking the epic spec
- proposing a minimal roadmap sync

### No orphan specs

Do not leave accepted specs orphaned from roadmap state.
If a spec is approved or implemented and it changes epic progress, the roadmap
must reflect it in the same session or the final handoff must call out the
missing roadmap sync explicitly.

### Canonical closure rule

A wave is only considered cleanly closed when:
- implementation landed
- spec is in canonical state
- roadmap status is synchronized
- any accepted follow-up/gap is explicitly recorded

### Exception — roadmap / feature-existence work

Para tarefas de priorização, roadmap, “devemos construir X?” ou “o que falta implementar?”, não comece por graph tools.

Comece por:
1. `~/bevox-knowledge/40_roadmap/company-os/2026-04-09-openclaw-company-os-roadmap.md`
2. `~/bevox-knowledge/40_roadmap/_shared/delivery-tracker.yml`
3. specs relevantes em `~/bevox-knowledge/35_specs/`
4. surfaces existentes em `src/app/api/` e `src/app/(dashboard)/`

Só depois use graph tools se ainda restar dúvida de implementação.

### Mandatory surface audit before proposing new MC work

Antes de propor nova página, rota, tab ou seção no Mission Control, você deve:
- procurar por rota/API existente pelo noun da feature
- procurar por page/tab existente pelo noun da feature
- citar a spec que introduziu a surface, se ela existir
- dizer explicitamente se a necessidade está:
  - já entregue
  - materialmente coberta mas tracker stale
  - ou ausente de fato

Se a surface já existir e cobrir materialmente a necessidade, proponha hygiene/refinement, não nova wave.

### Dense-codebase assumption

Assuma que o repositório já tem uma surface para a necessidade óbvia até provar o contrário.
Não use ausência na memória do agente como evidência de ausência no projeto.
